## Decision

Correct the page-zoom restrictions in a separately scoped product change. Replace `width=device-width,initial-scale=1,minimum-scale=1,maximum-scale=1,user-scalable=no,viewport-fit=cover` with `width=device-width,initial-scale=1,viewport-fit=cover`. Change `html{touch-action:pan-x pan-y}` to a policy that permits pinch zoom, such as `manipulation` or `auto`, and adjust `lockPageZoom()` so its document-level gesture, multi-touch, wheel, and keyboard handlers do not cancel user zoom. The viewport values set explicit scale bounds and disable user scaling; W3C’s ACT rule maps these viewport values to a failed expectation for resize text. It also notes that desktop browsers ignore the viewport meta element and that modern mobile browsers may ignore it or offer an accessibility override. [W3C ACT rule: Meta viewport allows for zoom](https://www.w3.org/WAI/standards-guidelines/act/rules/b4f0c3/)

The W3C Pointer Events specification says direct-manipulation zoom must conform to the `touch-action` values from the target through the document. `pan-x` and `pan-y` allow axis panning; `manipulation` allows panning and continuous zoom such as pinch. [W3C Pointer Events: `touch-action`](https://www.w3.org/TR/pointerevents3/#the-touch-action-css-property)

Keep `viewport-fit=cover`; the existing layout already uses safe-area environment insets. Remove `minimum-scale=1` as well so the author does not set a lower zoom bound. This report records a correction recommendation only; no proposed policy or handler change was implemented or tested.

Two separate follow-ups are supported by the same investigation: keyboard focus escapes the Settings overlay while it remains open, and Chrome’s desktop “Very large” font-size preference does not enlarge the app’s explicitly sized text. The focus finding is reproducible at 400% page zoom; the correction should move focus into the overlay, keep Tab navigation within it, and restore focus to the opener on close. The font preference finding is limited to the tested Chrome desktop setting; evaluate relative text sizing or another user-controlled text-size path in a separate UI change.

## Source audit

This is inspection of saved source, not runtime proof. [index.html](../index.html#L5) sets both viewport scale limits to `1` and disables user scaling. [index.html](../index.html#L75) sets `touch-action:pan-x pan-y`, which does not declare the continuous pinch-zoom behavior defined for `manipulation` in the W3C specification. The [document-level `lockPageZoom()` handlers](../index.html#L588) also cancel `gesturestart` / `gesturechange`, multi-touch `touchmove`, Ctrl/Meta-wheel, and Ctrl/Meta zoom keys. These three mechanisms all restrict zoom, so the synthetic pinch measurement below cannot attribute the unchanged scale to the viewport meta element alone. The page body and key headings use explicit pixel font sizes, while controls inherit those sizes ([index.html](../index.html#L76)). The layout includes `env(safe-area-inset-*)` padding and `viewport-fit=cover` ([index.html](../index.html#L77)). Its shared overlay is marked `role="dialog" aria-modal="true"`, but that markup alone does not keep keyboard focus inside it ([index.html](../index.html#L6266)).

The install instructions name Safari on iPhone and Chrome on Android ([index.html](../index.html#L6487)); they do not declare minimum supported browser or operating-system versions. No exact version floor was found in the README or development workflow. `BACKWARD_COMPATIBILITY.md` pins a sync-recovery protocol baseline, not a browser version. Therefore this audit records the two documented browser families without inferring version support.

## Executed proof

The complete browser runs used the app served locally from this worktree at `http://127.0.0.1:8780/`, with fresh temporary profiles and synthetic task data, on source `c08d08aa7d22cddaebe649d3cab4c7a2c639cad9`. The commands used the bundled Node and Playwright runtime: `desktop-zoom-evidence.cjs`, `desktop-reflow-400.cjs`, `mobile-emulation-evidence.cjs`, and `standalone-pwa-evidence.cjs`. Their JSON records name that source revision; logs and screenshots are in `.git/funsidething-task-evidence/arctic-observer-20261016/137/`.

The source comparison through `5ae2ba1f091910d3146f7c4dfae2a5664c6ba9a6` found only the changelog template’s fingerprint/copy and two FAQ copy lines changed in `index.html`, plus the service-worker cache fingerprint; the integration also added the offline typography audit and updated rationale metadata. That tip’s last commit only adjusted rationale metadata, and merge `27cb7041dc253cf62e23f44a1cd58614ad793e18` added the report only. The viewport, `touch-action`, `lockPageZoom()`, font, safe-area, dialog, and install-documentation source were unchanged across those revisions. A focused rerun on `991c2d1d5329dfb47107b65b485148a12aec3f36` reached native 200% Chrome zoom, then stopped when the startup motion dialog intercepted the following Settings click; that partial attempt is retained in the evidence folder and is not counted as a completed run. These are local rendered checks from fresh profiles; production, physical-device and ordinary-user account behavior were outside this run.

**Desktop Chrome and real browser page zoom.** Google Chrome `155.0.8059.80` on macOS `27.0.1` was controlled through Chrome’s own `chrome://settings/appearance` zoom selector. At 200%, `innerWidth` changed from 1440 to 720 CSS pixels and DPR from 1 to 2, while `visualViewport.scale` stayed 1. The document had no horizontal root overflow; scanner controls remained in the DOM; Settings’ Save settings and the FAQ dialog’s OK button were reachable after scrolling their contents. WCAG 1.4.4 permits a user agent’s page zoom as a text scaling mechanism when the content remains usable at 200%. [WCAG 2.2 Resize Text](https://www.w3.org/WAI/WCAG22/Understanding/resize-text.html)

At 400%, a 1280 × 1600 browser viewport became 320 × 400 CSS pixels at DPR 4. The document still had no horizontal root overflow, the Yes / No / Can’t scanner choices were reachable by vertical scrolling, and Settings’ Save settings button was visible at the bottom of its scroll area. W3C identifies 320 CSS pixels as the vertical reflow test width and 400% zoom in a 1280-pixel desktop window as a typical way to reach it. [WCAG 2.2 Reflow](https://www.w3.org/WAI/WCAG22/Understanding/reflow.html)

**Text-size preference.** With Chrome’s browser Font size set to “Very large,” the app still computed to `body=15px`, `h1=19px`, and scanner text `15px`; its explicit pixel sizing did not respond to that setting. WCAG 1.4.4 can still be met through a different supported mechanism such as page zoom, which worked at 200% above. This observation does not test Android’s separate accessibility font/page-zoom controls.

**Themes.** At 200% desktop zoom and in the 390 × 844 touch emulation, System, light, and dark modes were applied. The computed `color-scheme` and panel background paint changed with the selected theme; the standalone app also retained an explicitly selected dark theme at 200% zoom.

**Keyboard focus.** With Settings open at 400%, the active element remained the background Settings gear. The first Tab moved focus to the background “Enjoy the view” control. The next Tabs moved to the background Contexts heading and context buttons, then the underlying scanner’s Done and Edit controls, while the overlay remained open. The saved result is `desktop-reflow-400-results.json` (`focusSequence`); `desktop-settings-first-tab-400.png` captures the first transition. This is a reproducible keyboard-focus containment finding, independent of the viewport zoom restriction.

**Mobile-sized touch emulation.** Chrome `155.0.8059.80` ran on the same Mac desktop build with a 390 × 844 viewport, DPR 3, `isMobile`, and touch enabled. The reported user agent and platform remained macOS / `MacIntel`; these are desktop Chrome results configured for a mobile viewport and touch. A CDP-synthesized pinch over the visible scanner returned successfully but left `visualViewport.scale=1`, the viewport at 390 × 844, and DPR at 3. Because the page combines restrictive viewport values, `touch-action:pan-x pan-y`, and document-level gesture cancellation, this observation cannot identify which restriction (or emulation behavior) kept the measured scale at `1`; it does not establish physical mobile-browser behavior. Settings remained vertically scrollable with Save settings visible. Safe-area insets measured `0px` on all sides, so notched-device reachability was not tested.

**Installed mode.** In a separate fresh Chrome profile, CDP’s PWA install and launch commands installed the local manifest and launched a standalone app window. The service worker was active, `(display-mode: standalone)` matched, and the installed app retained 200% Chrome page zoom (`innerWidth=720`, DPR 2, `visualViewport.scale=1`). Settings’ Save settings remained reachable, and dark theme paint was applied. This installed-mode result is from a Chrome desktop PWA created through CDP; the iOS and Android home-screen flows were not exercised.

Chrome’s `visualViewport.scale` reports pinch zoom and is distinct from `devicePixelRatio`, which is why the page-zoom runs report both values. [Chrome: Introducing visualViewport](https://developer.chrome.com/blog/visual-viewport-api?hl=en) Google’s documentation also cautions that device emulation does not reproduce all mobile-browser features or bugs; a real device is needed for those claims. [Chrome: DevTools for mobile](https://developer.chrome.com/blog/devtools-mobile/)

## Limits and recommendation

The local machine had Safari `27.0.1`, but this run did not exercise Safari’s browser UI or zoom behavior. No iOS Simulator was available (`xcrun simctl` was unavailable), and `adb` was not installed. There was no physical iPhone or Android device in this investigation. Accordingly, actual iPhone Safari pinch, Android Chrome pinch/accessibility font scaling, their installed modes, and nonzero safe-area insets remain unverified. WebKit’s published iOS behavior says Safari on iOS 10 and later ignores `user-scalable`, `minimum-scale`, and `maximum-scale` for pinch zoom; that is platform documentation, not a test of the installed Safari version here. [WebKit: New Interaction Behaviors in iOS 10](https://webkit.org/blog/7367/new-interaction-behaviors-in-ios-10/). Chromium documents Android Chrome accessibility settings for page zoom and force-enabling zoom; those controls were not exercised on a device. [Chromium: Chrome Accessibility on Android](https://chromium.googlesource.com/chromium/src/+/HEAD/docs/accessibility/browser/android.md)

The evidence supports removing the author zoom locks from the viewport meta, `touch-action`, and `lockPageZoom()` handlers, while keeping physical iPhone/Android and safe-area proof as an explicit later validation item. No proposed correction was applied or tested. This investigation changed no executable source or test files. It is observational research/report work, so no test-first RED was applicable; the browser scripts above are direct rendered consumer checks. Physical-device validation and the project’s full release gate remain separate.
